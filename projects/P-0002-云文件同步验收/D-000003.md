# D-000003 · 云文件同步分层检查（脱敏节选）

记录日期：2026-11-06。性质：历史运维方法；本轮未跨机复测。保留分层验收与排查顺序；真实地址、主机名、私人路径、组网配置和回退指令未收录。

## 五、iCloud 与 SSH、OneDrive 分层验收

| 层 | 作用 | 健康证据 |
|---|---|---|
| EasyTier / SSH | 远程到达电脑 | 实际路由、SSH 与传输 |
| iCloud Obsidian | 两台 Mac 的本项目文档同步 | 单端修改自动到另一端、内容哈希一致 |
| OneDrive | 各资料节点本地与微软云盘同步 | 目标账号的本地与云端文件验证 |
| 节点A 的 Git 分发 | 从 节点A 推向 GitHub / VPS | 对应分发任务与提交记录 |

SSH 可用不代表 iCloud 正常；手工补拷后两端一致也不证明同步恢复。节点A 的 Git 分发与 iCloud 是不同机制，不在 节点B 运行旧 `vsync`，也不靠 Git 推送修复 Mac 间的 iCloud 文件问题。


## 六、iCloud 排查与修复顺序
1. 两端核对完整路径、实际文件名、大小和 SHA-256，确认不是 Obsidian 搜索或侧栏没刷新。
2. 查看对应容器状态，例如 `brctl status iCloud.md.obsidian`；last-sync、needs-sync 和待处理项目只是线索，以实际新内容跨机到达为准。
3. 检查网络、磁盘空间、iCloud 账号状态和可用配额。待同步不等于数据损坏，先给出有限观察时间。
4. 单端写入唯一内容，在另一端只读观察；再反向测试。多端同时创建同名文件会干扰判断并可能产生重复副本。
5. 确认当前同步确实停住时，再考虑请求下载、重新打开相关目录或重启用户同步进程；操作前保护本地未上传内容。
6. 不先退出 iCloud 账号、不清理 CloudDocs 数据库、不批量删除占位文件。需要这些更大操作时，先有完整备份和明确原因。
7. 重复副本先校验内容；完全相同时备份后清理一端，让删除自动传播；内容不同时保留差异，不能凭“2.md”名字认定可删除。
8. 验收完整项目的文件清单、哈希、重复副本和至少一次反向同步。若仍靠 SSH 补拷，应标“临时交付”，不能标“iCloud 已修复”。
